# 👤 멘티 - 최지아 데모 가이드

## 1. 📄 채용공고 정보
* **공고명**: 대규모 트래픽 분산 처리 백엔드 개발자
* **업무 자격요건**:
  * Java 및 Spring Boot 기반 백엔드 애플리케이션 개발 역량
  * JPA, Hibernate 등 ORM 프레임워크 활용 및 엔티티 설계 경험
  * RESTful API 설계 규칙에 대한 이해 및 설계 유경험자
  * RDBMS(MySQL 등)의 인덱스 최적화 및 동시성 제어 능력
* **인재상**:
  * 장애 발생 시 집요하게 분석하여 해결책을 도출하는 끈기 있는 인재
  * 고품질 아키텍처와 성능 최적화에 대한 책임감을 지닌 신뢰형 인재
  * 끊임없이 새로운 분산 처리 기법을 탐구하고 지식을 공유하는 학습형 인재
* **우대사항**:
  * Redis 등 인메모리 DB를 활용한 분산 락 및 캐싱 구축 경험
  * Kafka, RabbitMQ 등 메시지 큐 기반 비동기 파이프라인 연동 경험
  * nGrinder, JMeter 등을 사용한 부하 테스트 및 모니터링 메트릭 분석 경험

## 2. 📝 자기소개서 내용

### [지원동기]
저는 대규모 트래픽 환경에서 한 치의 오차도 없이 안정적으로 동작하는 백엔드 시스템을 설계하고 구축하는 것에 깊은 열정을 품고 있습니다. 대학 시절 진행했던 이커머스 플랫폼 토이 프로젝트에서, 대형 할인 이벤트 상황을 가정하고 동시 접속자 수를 증가시키는 부하 테스트를 진행한 적이 있습니다. 이때 서버가 응답 불능 상태에 빠지는 것을 목격하고, 트래픽 폭증이 서비스에 미치는 치명적인 영향력을 뼈저리게 느꼈습니다. 단순한 기능 구현을 넘어, 분산 환경에서의 데이터 정합성 유지와 서버 자원의 최적화가 백엔드 개발자로서의 진정한 전문성이라는 확신을 얻게 되었습니다. 귀사는 혁신적인 모의 면접 서비스를 통해 매일 수만 명의 사용자에게 실시간 영상 및 오디오 스트리밍과 데이터 분석 리포트를 제공하며 급격히 성장하고 있습니다. 이러한 대규모 트래픽 속에서도 무중단 서비스를 제공하고, 아키텍처 수준에서의 성능 튜닝을 통해 인프라 비용을 절감하는 도전에 직접 동참하고자 지원하였습니다. 그동안 학습한 고성능 아키텍처 설계를 바탕으로 서비스의 안정적인 성장에 든든한 초석이 되겠습니다.

### [본인의 강점과 약점]
저의 가장 큰 강점은 복잡한 성능 장애 상황에서 원인을 집요하게 파헤치는 분석력과 끈기입니다. 문제 상황을 마주했을 때 감에 의존하지 않고, Prometheus와 Grafana 같은 모의 모니터링 도구를 활용해 스레드 덤프와 힙 메모리 덤프를 분석하며 근본적인 병목 지점을 수치화해 찾아내는 것을 즐깁니다. 이를 통해 동시성 문제를 명확히 제어하며 시스템을 견고하게 개선해 나갑니다. 반면, 저의 약점은 아키텍처의 완벽성과 성능 최적화에 지나치게 몰두한 나머지 개발 마일스톤에 명시된 초기 일정 설정을 다소 타이트하게 가져가는 경향이 있다는 점입니다. 과도한 최적화로 인해 마케팅이나 기획 부서와의 일정 협의 과정에서 마찰이 생기지 않도록, 최근에는 MVP 개발 단계와 성능 고도화 단계를 철저히 분리하여 기록하는 습관을 들이고 있습니다. 이를 통해 비즈니스 요구사항과 기술적 고도화 사이의 균형 감각을 기르며, 협업 부서의 일정 조율 요구사항에 보다 유연하게 대처할 수 있도록 스스로를 보완하고 있습니다.

### [실무/프로젝트 문제 해결 경험]
이커머스 웹 애플리케이션 프로젝트에서 한정판 선착순 쿠폰 발급 이벤트를 진행할 때 발생했던 심각한 동시성 이슈와 데이터 정합성 문제를 해결한 경험이 있습니다. 초기에 아무런 락 장치 없이 이벤트를 오픈하자 데이터베이스에 수많은 쓰기 요청이 몰려 커넥션 풀이 순식간에 고갈되었고, 최종적으로 준비된 쿠폰 수량보다 더 많은 쿠폰이 발급되는 동시성 정합성 위반 오류가 발생했습니다. 문제를 해결하기 위해 먼저 Redis의 분산 락(Redisson)을 도입하여 동일한 사용자와 한정된 자원에 대해 원자적 연산을 보장하도록 개선했습니다. 또한, DB에 가해지는 직접적인 부하를 낮추기 위해 Lua 스크립트를 작성하여 남은 쿠폰 수량의 차감을 메모리 상의 Redis 내에서 1차로 검증하도록 변경하였고, 통과된 요청에 한해서만 Kafka 메시지 큐를 통해 DB에 비동기적으로 기록하도록 파이프라인을 설계했습니다. 그 결과, 초당 3,000건의 동시 요청이 발생하는 상황에서도 쿠폰의 초과 발급 없이 데이터 정합성을 완벽히 유지했으며, 평균 API 응답 시간 또한 기존 대비 약 75% 단축시키는 성과를 거두었습니다.

* **답변**:
 > "프로덕션 대규모 트래픽 환경에서는 Prometheus를 활용해 JVM 메트릭, 즉 액티브 스레드 수, GC 발생 빈도, 힙 메모리 사용량을 실시간으로 수집하고, Grafana 대시보드로 시각화하는 모니터링 체계를 구축하겠습니다. 특히 커넥션 풀 고갈을 예방하기 위해 HikariCP의 활성 커넥션 수와 대기 시간 메트릭을 유심히 관찰할 것입니다. 수집된 메트릭은 Alertmanager와 연동하여 커넥션 획득 대기 시간이 500ms를 초과하거나 API 에러율이 1%를 초과하는 즉시 Slack을 통해 알림이 발송되도록 구성하여 즉각적인 분석 및 대응이 가능한 운영 체계를 마련하겠습니다. 추가로 Pinpoint APM을 도입하여 서비스 간 분산 트레이싱을 연계 분석하겠습니다."

### ❓ [개인 질문 1 (추천 1번)]
* **질문**: "한정판 선착순 쿠폰 발급 프로젝트에서 Redis의 Redisson 분산 락을 선택하셨는데, Lettuce의 스핀 락 방식 대신 Redisson의 Pub/Sub 기반 락을 선택하여 얻은 성능적 이점은 구체적으로 무엇인가요?"
* **답변**:
 > "Lettuce의 스핀 락 방식은 락을 획득할 때까지 지속적으로 Redis에 `SETNX` 요청을 폴링하기 때문에 락 획득 시도를 할 때마다 Redis의 CPU 리소스를 낭비하고 네트워크 오버헤드를 발생시킵니다. 반면, Redisson은 Redis의 Pub/Sub 기능을 활용합니다. 락을 획득하지 못한 클라이언트는 락 해제 채널을 구독하고 대기하다가, 기존 락 보유자가 락을 해제하며 발행하는 메시지를 수신했을 때 한 번만 다시 획득 시도를 하므로 불필요한 폴링 부하를 완벽히 해소합니다. 또한, 내부적으로 보관 연장 메커니즘을 제공하여 비즈니스 로직 처리 중 락 만료로 인한 동시성 깨짐을 안전하게 예방할 수 있는 강점이 있습니다."

### ❓ [개인 질문 2 (추가 질문)]
* **질문**: "대규모 트래픽 상황에서 DB 커넥션 풀 고갈 문제를 방지하기 위해 커넥션 풀 크기를 튜닝하거나 애플리케이션 레벨에서 고려해야 할 최적화 방안은 무엇인가요?"
* **답변**:
 > "커넥션 풀 최적화를 위해 무조건 풀 크기를 늘리기보다는, 톰캣 스레드 수와 DB CPU 코어 수의 관계를 고려해야 합니다. HikariCP 공식 가이드의 공식을 참고하여 스레드 경쟁 비용을 줄이는 크기로 설정했습니다. 그리고 애플리케이션 레벨에서는 트랜잭션 범위를 좁히는 것이 핵심입니다. 서비스 단 전체에 걸쳐 `@Transactional`을 붙이기보다 데이터 쓰기나 갱신이 일어나는 특정 지점으로 범위를 좁혔고, 단순 조회 쿼리는 `readOnly = true`를 활성화해 변경 감지 오버헤드를 막고 커넥션을 빨리 반환하도록 유도했습니다. 또한 OSIV 설정을 비활성화함으로써 뷰 렌더링 영역까지 커넥션이 유지되는 시간을 방지해 풀 고갈을 예방했습니다."
